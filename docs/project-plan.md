# Moras 프로젝트 계획

## 1. 프로젝트 개요

Moras는 오픈채팅 커뮤니티 이벤트용 웹 애플리케이션이다. 참가자는 DB에 미리 등록된 본인을 선택하고 MBTI와 생년월일시를 입력한다. 시스템은 `@fullstackfamily/manseryeok`로 사주/만세력 정보를 계산하고, Gemini API로 MBTI와 사주/만세력 기반 방향성 점수를 생성해 평균 점수가 가장 높은 남녀 조합을 1:1로 매칭한다. 생년월일시 원본은 공개 화면에 노출하지 않고 관리자 화면에서만 조회하며, 매칭에는 MBTI와 계산된 만세력 결과를 사용한다.

동시에 Moras는 NStack을 실제 제품 개발에 적용해 검증하는 파일럿 애플리케이션이다. 따라서 Moras의 성공 기준은 제품 기능 완성뿐 아니라, NStack의 작업 지시서, 구현, 검증, 보고서, LLMWiki 지식화 흐름이 실전 프로젝트에서 얼마나 잘 작동하는지 확인하는 데에도 있다.

## 2. 기획 의도

현재 오픈채팅에서 진행되는 이벤트를 웹앱 기반으로 전환한다. 참가자는 불필요한 페이지를 거치지 않고 안내에 따라 본인 선택, MBTI 입력, 생년월일시 입력, 만세력 계산을 완료한다. 운영자는 전체 입력이 끝난 뒤 일괄 매칭을 실행하고 결과를 검토, 발표할 수 있어야 한다.

핵심 경험은 다음과 같다.

- MBTI가 주는 익숙함
- 사주가 주는 상징적 해석과 재미
- 짧고 가벼운 이벤트 참여 흐름
- 운영자가 최종 결과를 검토하고 조정할 수 있는 구조
- 평균 점수와 상세 이유를 보여주는 결과 확인 흐름
- 매칭된 남녀가 각각 비밀스럽게 선택 여부를 투표하는 흐름

NStack 관점의 핵심 의도는 다음과 같다.

- NStack이 신규 프로젝트 초기화부터 실제 배포까지 감당할 수 있는지 검증
- 작업 지시서와 완료 보고서가 구현 품질을 끌어올리는지 검증
- LLMWiki/SwarmVault가 제품 지식과 작업 히스토리를 재사용 가능한 자산으로 만드는지 검증
- Netlify, Supabase, GitHub, NStack이 하나의 개발 흐름으로 자연스럽게 연결되는지 검증
- 반복 작업 중 NStack 규칙과 스킬에서 개선해야 할 지점을 발견

## 3. 이름과 브랜드 의미

| 요소 | 의미 |
|---|---|
| M | MBTI, Mind, Match |
| Oracle | 사람의 성향과 관계 흐름을 해석하는 상징 |
| S | Saju, Sync, Soul |

제품 톤은 가볍고 신비롭되, 과하게 무겁거나 운명론적으로 보이지 않게 한다. 참가자의 개인정보를 다루는 만큼 화면과 문구는 신뢰감 있게 구성한다.

## 4. 사용자

### 참가자

오픈채팅 매칭 이벤트에 참여하는 사람이다.

필요한 것:

- 이벤트 내용을 빠르게 이해
- 큰 마찰 없이 정보 입력
- 제출 정보가 이벤트 목적에만 쓰인다는 신뢰
- 재미있는 방식으로 매칭 결과에 참여

### 운영자

이벤트를 진행하고 매칭 결과를 관리하는 사람이다.

필요한 것:

- 제출된 참가자 목록 확인
- 성별, MBTI, 제출 상태 기준 필터
- 매칭 점수 계산 실행
- 점수 상세 내역 확인
- 최종 매칭 조정 또는 확정
- 결과 발표 또는 안내 준비

### NStack 검증자

Moras를 통해 NStack의 실제 개발 적용성을 확인하는 사람이다.

필요한 것:

- 각 단계의 지시서, 구현, 검증, 보고서가 남는지 확인
- LLMWiki에 프로젝트 지식이 누적되는지 확인
- 새 프로젝트에서 NStack 설치와 외부 리소스 연결이 반복 가능하게 동작하는지 확인
- 구현 중 발견된 NStack 규칙/스킬 개선점을 추적

## 5. MVP 범위

상세 이벤트 플로우는 `docs/product/moras-event-flow-spec.md`를 기준으로 한다.

### 참가자 화면

- 참가자 입력 화면
- DB에 미리 등록된 참가자 목록 드롭다운
- MBTI 직접 입력 또는 선택
- 생년월일 입력
- 출생시간 입력
- 양력/음력 선택
- 출생 지역 또는 경도 입력
- 서버 측 만세력 자동 계산
- 생년월일시 원본 공개 화면 미노출 및 관리자 전용 조회
- 개인정보 및 이벤트 이용 동의
- 제출 완료 화면

### 운영자 화면

- 별도 관리자 페이지
- 관리자 패스코드 또는 운영자 전용 접근 키
- 참가자 목록
- 성별, MBTI, 제출 상태 필터
- 참가자 상세 보기
- 참가자별 비밀투표 코드 생성 또는 재생성
- 매칭 계산 실행
- 매칭 결과 테이블
- 남녀 쌍별 점수 상세 내역
- 1등 매칭 하이라이트
- 비밀 투표 결과 확인
- 운영자 메모와 최종 확정 표시

### 매칭 엔진

- `@fullstackfamily/manseryeok` 기반 만세력 계산
- Gemini API 기반 개인 관점별 방향성 궁합 점수
- 남자 기준 여자 점수
- 여자 기준 남자 점수
- 평균 점수 기반 최종 점수
- 동일 참가자 중복 매칭 방지
- 성비가 맞지 않을 때 적은 쪽 기준 1:1 강제 매칭
- 운영자와 참가자가 이해할 수 있는 상세 매칭 이유

초기 점수 모델:

| 구성 요소 | 설명 |
|---|---|
| `male_to_female_score` | 남자 입장에서 여자와의 궁합 점수 |
| `female_to_male_score` | 여자 입장에서 남자와의 궁합 점수 |
| `average_score` | 두 점수의 평균. 최종 매칭 정렬 기준 |
| `reason_summary` | 공개용 매칭 이유 요약 |
| `male_reason` / `female_reason` | 각 참가자 관점의 상세 이유 |

### 접근 방식

MVP에서는 참가자 회원가입/로그인을 넣지 않는다. 참가자 입력과 결과 확인 흐름은 공개 접근을 전제로 하되, 운영자 페이지는 관리자 패스코드 또는 운영자 전용 접근 키로 보호한다.

이 결정은 첫 이벤트를 빠르게 검증하기 위한 것이다. 대신 참가자 인증이 없다는 전제를 제품 설계에 반영해 민감한 개인정보 수집과 화면 노출을 최소화한다.

## 9. 보안과 개인정보 원칙

Moras는 생년월일, 출생시간, 연락 또는 식별 정보처럼 민감할 수 있는 데이터를 다룬다.

원칙:

- 이벤트에 필요한 최소 정보만 수집한다.
- 참가자 인증이 없는 MVP이므로 공개 화면에는 공개되어도 되는 정보만 표시한다.
- 공개 테이블에는 RLS를 활성화한다.
- 참가자 제출은 가능하되, 민감한 연락처나 출생 정보는 공개 화면에 그대로 노출하지 않는다.
- 운영자용 기능은 관리자 패스코드 또는 운영자 전용 접근 키로 보호한다.
- 비밀투표 코드는 투표 당사자와 운영자만 알 수 있게 전달하고, DB에는 원문 대신 해시만 저장한다.
- service role key는 서버 환경변수에만 둔다.
- 사주 결과를 운명처럼 단정하지 않는다.
- 개인정보 이용 동의 문구를 명확히 제공한다.

목표: 실행 가능한 웹앱 기본 구조를 만든다.

- migration 적용

목표: 참가자가 이벤트 정보를 제출할 수 있게 한다.

- DB 참가자 후보 드롭다운 구현
- 참가자 폼 구현
- MBTI 직접 입력 또는 선택 구현
- 생년월일/출생시간 입력 구현
- 출생 지역 또는 경도 입력 구현
- 서버 측 만세력 계산 구현
- 동의 체크 구현
- 입력 검증과 제출 처리
- 제출 완료 화면 구현

완료 기준:

- 공개 페이지에서 참가자 제출 가능
- DB에 미리 등록된 본인을 선택 가능
- 생년월일시로 만세력이 계산되고, 입력 원본은 공개 화면에 노출되지 않으며 관리자 화면에서만 조회
- 잘못된 입력 차단
- 제출 데이터가 Supabase에 저장

### Phase 4. 운영자 화면

목표: 운영자가 참가자를 관리할 수 있게 한다.

작업:

- 관리자 패스코드 또는 운영자 전용 접근 키가 필요한 운영자 화면 구성
- 참가자 목록 구현
- 필터 구현
- 참가자 상세 패널 구현
- 참가자별 비밀투표 코드 생성/재생성 구현
- 이벤트 상태 표시

완료 기준:

- 운영자가 제출된 참가자를 보고 필터링 가능
- 운영자 페이지는 관리자 패스코드 또는 운영자 전용 접근 키 없이는 사용할 수 없음
- 운영자가 참가자별 비밀투표 코드를 생성하거나 재생성 가능
- 공개 화면에서는 민감정보 노출이 최소화됨

### Phase 5. 매칭 엔진

목표: 매칭 점수를 계산하고 결과를 검토할 수 있게 한다.

작업:

- `@fullstackfamily/manseryeok` 기반 만세력 계산 결과 사용
- Gemini API 기반 개인 관점별 반대 성별 전체 대상 점수 생성
- 남자 기준 여자 점수와 여자 기준 남자 점수를 방향성 평가로 저장
- 양방향 점수를 남녀 조합별 평균 점수로 집계
- 평균 점수 계산
- 남녀 조합별 결과 생성
- 전체 평균 점수 합이 최대가 되는 최적 1:1 매칭 계산
- 적은 성별 기준 1:1 강제 매칭
- 중복 최종 매칭 방지
- 매칭 실행과 결과 저장
- 상세 이유 저장
- 비밀 투표 저장

완료 기준:

- 운영자가 매칭 계산 실행 가능
- 결과에 점수 상세 내역 포함
- 1등 매칭이 하이라이트됨
- 상세 페이지에서 이유와 투표 버튼 표시
- 결과가 DB에 저장

### Phase 6. 배포

목표: Moras를 외부에서 접속 가능하게 만든다.

작업:

- Netlify 프로젝트 생성 또는 연결
- 환경변수 등록
- Preview 배포
- Production 배포
- 공개 입력, 운영자 진행, 결과, 상세, 투표 경로 smoke test

완료 기준:

- 공개 URL 접속 가능
- 배포 환경에서 Supabase 저장 동작
- 배포 환경에서 Gemini API 호출이 서버 측에서만 동작
- 운영자 페이지 보호가 배포 환경에서 동작
- 참가자 인증 없는 공개 접근 전제에서 민감정보 노출이 최소화됨

### Phase 7. 첫 이벤트 준비

목표: 첫 실제 이벤트를 운영 가능한 상태로 만든다.

작업:

- 이벤트 레코드 생성
- 동의 문구 확정
- 모바일 제출 테스트
- 샘플 매칭 실행
- 운영자용 진행 문서 작성

완료 기준:

- end-to-end 리허설 완료
- 운영자가 개발자 도움 없이 이벤트 진행 가능

### Phase 8. NStack 파일럿 회고

목표: Moras 개발 과정에서 NStack이 실제 제품 개발에 얼마나 효과적이었는지 평가한다.

작업:

- 각 단계별 지시서/보고서/LLMWiki 기록 누락 여부 확인
- 작업 흐름 중 병목과 반복 오류 정리
- NStack 스킬, 규칙, 문서에서 개선할 항목 도출
- 통합 지식체계에 Moras 파일럿 결과 기록
- 다음 NStack 기반 프로젝트에 적용할 권장 절차 정리

완료 기준:

- NStack 파일럿 회고 보고서 작성
- 개선 항목이 작업 목록 또는 이슈로 분리
- Moras 개발 경험이 LLMWiki에 통합

## 11. 첫 구현 순서

권장 순서:

1. `Next.js + Tailwind + Supabase` 앱 골격 생성

4. Gemini API 서버 환경변수와 서버 route/function 추가

6. 참가자 후보 seed와 드롭다운 제출 흐름 구현

8. 운영자 페이지 보호와 비밀투표 코드 생성 구현
9. Gemini 점수 생성 dry run
10. 일괄 매칭 실행 구현

## 14. 완료 정의

제품 MVP는 다음 조건을 만족하면 완료로 본다.

- 참가자가 공개 페이지에서 프로필을 제출할 수 있다.
- 운영자가 참가자를 확인할 수 있다.
- 운영자가 매칭 결과를 계산할 수 있다.
- 매칭 결과에 설명 가능한 점수 상세 내역이 있다.
- 1등 매칭이 하이라이트된다.
- 매칭 상세에서 남녀가 각각 비밀 투표를 할 수 있다.
- 데이터가 RLS가 적용된 Supabase에 저장된다.
- Gemini API 키가 클라이언트에 노출되지 않는다.
- 앱이 Netlify에 배포된다.
- 첫 이벤트 리허설이 데스크톱과 모바일에서 통과한다.

NStack 파일럿은 다음 조건을 만족하면 성공으로 본다.

- 각 Phase마다 작업 지시서와 완료 보고서가 남아 있다.
- 주요 의사결정과 구현 지식이 LLMWiki에 기록되어 있다.
- Supabase, Netlify, GitHub, SwarmVault 연결 절차가 재현 가능하게 정리되어 있다.
- NStack 스킬과 규칙의 개선점이 구체적으로 도출되어 있다.
- Moras 경험을 다음 프로젝트의 표준 절차로 재사용할 수 있다.

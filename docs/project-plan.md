# Moras 프로젝트 계획

## 1. 프로젝트 개요

Moras는 오픈채팅 커뮤니티 이벤트용 웹 애플리케이션이다. 참가자는 MBTI와 사주 관련 출생 정보를 입력하고, 시스템은 궁합 점수를 계산해 가장 잘 맞는 남녀 매칭 후보를 추천한다.

동시에 Moras는 NStack을 실제 제품 개발에 적용해 검증하는 파일럿 애플리케이션이다. 따라서 Moras의 성공 기준은 제품 기능 완성뿐 아니라, NStack의 작업 지시서, 구현, 검증, 보고서, LLMWiki 지식화 흐름이 실전 프로젝트에서 얼마나 잘 작동하는지 확인하는 데에도 있다.

## 2. 기획 의도

현재 오픈채팅에서 진행되는 이벤트를 웹앱 기반으로 전환한다. 참가자는 정보를 쉽게 제출하고, 운영자는 제출된 정보를 기반으로 매칭 결과를 계산, 검토, 발표할 수 있어야 한다.

핵심 경험은 다음과 같다.

- MBTI가 주는 익숙함
- 사주가 주는 상징적 해석과 재미
- 짧고 가벼운 이벤트 참여 흐름
- 운영자가 최종 결과를 검토하고 조정할 수 있는 구조

NStack 관점의 핵심 의도는 다음과 같다.

- NStack이 신규 프로젝트 초기화부터 실제 배포까지 감당할 수 있는지 검증
- 작업 지시서와 완료 보고서가 구현 품질을 끌어올리는지 검증
- LLMWiki/SwarmVault가 제품 지식과 작업 히스토리를 재사용 가능한 자산으로 만드는지 검증
- Netlify, Supabase, GitHub, NStack이 하나의 개발 흐름으로 자연스럽게 연결되는지 검증
- 반복 작업 중 NStack 규칙과 스킬에서 개선해야 할 지점을 발견

## 3. 이름과 브랜드 의미

| 요소 | 의미 |
|---|---|
| M | MBTI, Mind, Match |
| Oracle | 사람의 성향과 관계 흐름을 해석하는 상징 |
| S | Saju, Sync, Soul |

제품 톤은 가볍고 신비롭되, 과하게 무겁거나 운명론적으로 보이지 않게 한다. 참가자의 개인정보를 다루는 만큼 화면과 문구는 신뢰감 있게 구성한다.

## 4. 사용자

### 참가자

오픈채팅 매칭 이벤트에 참여하는 사람이다.

필요한 것:

- 이벤트 내용을 빠르게 이해
- 큰 마찰 없이 정보 입력
- 제출 정보가 이벤트 목적에만 쓰인다는 신뢰
- 재미있는 방식으로 매칭 결과에 참여

### 운영자

이벤트를 진행하고 매칭 결과를 관리하는 사람이다.

필요한 것:

- 제출된 참가자 목록 확인
- 성별, MBTI, 제출 상태 기준 필터
- 매칭 점수 계산 실행
- 점수 상세 내역 확인
- 최종 매칭 조정 또는 확정
- 결과 발표 또는 안내 준비

### NStack 검증자

Moras를 통해 NStack의 실제 개발 적용성을 확인하는 사람이다.

필요한 것:

- 각 단계의 지시서, 구현, 검증, 보고서가 남는지 확인
- LLMWiki에 프로젝트 지식이 누적되는지 확인
- 새 프로젝트에서 NStack 설치와 외부 리소스 연결이 반복 가능하게 동작하는지 확인
- 구현 중 발견된 NStack 규칙/스킬 개선점을 추적

## 5. MVP 범위

### 참가자 화면

- 이벤트 입장 화면
- 참가자 정보 입력 폼
- 성별 선택
- 닉네임 또는 표시 이름
- 연락처 또는 이벤트 식별 정보
- MBTI 선택
- 생년월일 입력
- 출생시간 입력
- 양력/음력 선택
- 개인정보 및 이벤트 이용 동의
- 제출 완료 화면

### 운영자 화면

- 관리자 로그인 또는 접근 제한
- 참가자 목록
- 성별, MBTI, 제출 상태 필터
- 참가자 상세 보기
- 매칭 계산 실행
- 매칭 결과 테이블
- 남녀 쌍별 점수 상세 내역
- 운영자 메모와 최종 확정 표시

### 매칭 엔진

- MBTI 궁합 점수
- 사주 기반 기질 점수
- 이벤트 보정 점수
- 가중치 기반 최종 점수
- 동일 참가자 중복 매칭 방지
- 운영자가 이해할 수 있는 점수 설명

초기 점수 가중치:

| 구성 요소 | 가중치 | MVP 기준 |
|---|---:|---|
| MBTI 궁합 | 50% | 유형과 지표 조합 기반 |
| 사주 기질 | 40% | 오행/기질을 단순화한 모델 |
| 이벤트 보정 | 10% | 나이 차이, 입력 완성도, 운영자 보정 |

## 6. MVP에서 제외할 것

- 전문적인 전체 사주 해석 엔진
- 결제 기능
- 참가자용 공개 결과 공유 페이지
- 실시간 채팅
- 여러 이벤트를 동시에 관리하는 멀티 테넌트 구조
- 카카오톡/오픈채팅 자동 연동
- AI 성향 리포트 생성

위 항목은 첫 이벤트 흐름이 안정화된 뒤 고도화 단계에서 검토한다.

## 8. 데이터 모델 초안

### events

매칭 이벤트 정보를 저장한다.

- `id`
- `name`
- `slug`
- `status`
- `starts_at`
- `ends_at`
- `created_at`

### participants

참가자 제출 정보를 저장한다.

- `id`
- `event_id`
- `gender`
- `display_name`
- `contact`
- `mbti`
- `birth_date`
- `birth_time`
- `calendar_type`
- `consent_accepted`
- `submitted_at`
- `created_at`

### match_runs

매칭 계산 실행 단위를 저장한다.

- `id`
- `event_id`
- `status`
- `created_by`
- `created_at`

### match_results

남녀 참가자 쌍별 매칭 점수를 저장한다.

- `id`
- `match_run_id`
- `male_participant_id`
- `female_participant_id`
- `mbti_score`
- `saju_score`
- `balance_score`
- `total_score`
- `breakdown`
- `rank`
- `is_final`
- `operator_note`

### 관리자 접근

MVP에서는 두 가지 방식 중 하나로 시작할 수 있다.

- Supabase Auth 사용자 허용 목록
- 환경변수 기반 관리자 패스코드

운영자가 여러 명이면 Supabase Auth가 낫고, 첫 폐쇄형 이벤트를 빠르게 검증하려면 관리자 패스코드 방식이 더 빠르다.

## 9. 보안과 개인정보 원칙

Moras는 생년월일, 출생시간, 연락 또는 식별 정보처럼 민감할 수 있는 데이터를 다룬다.

원칙:

- 이벤트에 필요한 최소 정보만 수집한다.
- 참가자 목록은 공개하지 않는다.
- 공개 테이블에는 RLS를 활성화한다.
- 참가자는 제출만 가능하고 전체 참가자 목록을 읽을 수 없어야 한다.
- 관리자 조회와 수정은 인증된 관리자 또는 서버 측 권한으로만 처리한다.
- service role key는 서버 환경변수에만 둔다.
- 사주 결과를 운명처럼 단정하지 않는다.
- 개인정보 이용 동의 문구를 명확히 제공한다.

## 10. 개발 단계

### Phase 0. 계획과 준비

상태: 진행 중

작업:

- 제품 브리프 작성
- 프로젝트 계획 작성
- 외부 서비스 연결 확인
- Supabase 프로젝트 생성
- NStack/LLMWiki 준비

완료 기준:

- 프로젝트 계획 승인
- 기술 스택 확정
- NStack 파일럿 검증 기준 문서화

### Phase 1. 앱 골격 생성

목표: 실행 가능한 웹앱 기본 구조를 만든다.

작업:

- Next.js 프로젝트 생성
- Tailwind CSS 설정
- Supabase client 추가
- Netlify 설정 추가
- 환경변수 예시 파일 추가
- 초기 화면 라우트 생성

완료 기준:

- 로컬 개발 서버 실행
- 기본 화면 렌더링
- 빌드 성공

### Phase 2. 데이터베이스 기반

목표: 첫 운영 가능한 DB 스키마를 만든다.

작업:

- Supabase migration 작성
- `events`, `participants`, `match_runs`, `match_results` 생성
- RLS 활성화
- 참가자 제출용 insert 정책 추가
- 관리자 또는 서버 접근 방식 추가

완료 기준:

- migration 적용
- Supabase에서 테이블 확인
- 기본 insert/query 테스트 통과

### Phase 3. 참가자 제출 흐름

목표: 참가자가 이벤트 정보를 제출할 수 있게 한다.

작업:

- 이벤트 입장 화면 구현
- 참가자 폼 구현
- MBTI 선택 구현
- 생년월일/출생시간 입력 구현
- 동의 체크 구현
- 입력 검증과 제출 처리
- 제출 완료 화면 구현

완료 기준:

- 공개 페이지에서 참가자 제출 가능
- 잘못된 입력 차단
- 제출 데이터가 Supabase에 저장

### Phase 4. 운영자 화면

목표: 운영자가 참가자를 관리할 수 있게 한다.

작업:

- 관리자 접근 제한 추가
- 참가자 목록 구현
- 필터 구현
- 참가자 상세 패널 구현
- 이벤트 상태 표시

완료 기준:

- 운영자가 제출된 참가자를 보고 필터링 가능
- 일반 참가자는 관리자 데이터에 접근 불가

### Phase 5. 매칭 엔진

목표: 매칭 점수를 계산하고 결과를 검토할 수 있게 한다.

작업:

- MBTI 점수 모델 구현
- 단순화된 사주 기질 모델 구현
- 최종 가중 점수 구현
- 남녀 조합별 결과 생성
- 중복 최종 매칭 방지
- 매칭 실행과 결과 저장

완료 기준:

- 운영자가 매칭 계산 실행 가능
- 결과에 점수 상세 내역 포함
- 결과가 DB에 저장

### Phase 6. 배포

목표: Moras를 외부에서 접속 가능하게 만든다.

작업:

- Netlify 프로젝트 생성 또는 연결
- 환경변수 등록
- Preview 배포
- Production 배포
- 공개 폼과 관리자 경로 smoke test

완료 기준:

- 공개 URL 접속 가능
- 배포 환경에서 Supabase 저장 동작
- 관리자 경로 접근 제어 동작

### Phase 7. 첫 이벤트 준비

목표: 첫 실제 이벤트를 운영 가능한 상태로 만든다.

작업:

- 이벤트 레코드 생성
- 동의 문구 확정
- 모바일 제출 테스트
- 샘플 매칭 실행
- 운영자용 진행 문서 작성

완료 기준:

- end-to-end 리허설 완료
- 운영자가 개발자 도움 없이 이벤트 진행 가능

### Phase 8. NStack 파일럿 회고

목표: Moras 개발 과정에서 NStack이 실제 제품 개발에 얼마나 효과적이었는지 평가한다.

작업:

- 각 단계별 지시서/보고서/LLMWiki 기록 누락 여부 확인
- 작업 흐름 중 병목과 반복 오류 정리
- NStack 스킬, 규칙, 문서에서 개선할 항목 도출
- 통합 지식체계에 Moras 파일럿 결과 기록
- 다음 NStack 기반 프로젝트에 적용할 권장 절차 정리

완료 기준:

- NStack 파일럿 회고 보고서 작성
- 개선 항목이 작업 목록 또는 이슈로 분리
- Moras 개발 경험이 LLMWiki에 통합

## 11. 첫 구현 순서

| 사주 결과 과신 | 사용자가 결과를 과하게 믿을 수 있음 | 이벤트용 궁합 안내로 표현 |
| 개인정보 처리 | 신뢰와 법적 리스크 | 최소 수집, RLS, 동의 문구 |
| 관리자 화면 노출 | 참가자 정보 유출 | 인증과 서버 측 권한 사용 |
| 매칭 공정성 의문 | 결과 신뢰 저하 | 점수 구성 요소 설명 |
| 이벤트 트래픽 급증 | 제출 실패 가능 | 단순한 구조로 시작하고 사전 배포 테스트 |

## 14. 완료 정의

제품 MVP는 다음 조건을 만족하면 완료로 본다.

- 참가자가 공개 페이지에서 프로필을 제출할 수 있다.
- 운영자가 참가자를 확인할 수 있다.
- 운영자가 매칭 결과를 계산할 수 있다.
- 매칭 결과에 설명 가능한 점수 상세 내역이 있다.
- 데이터가 RLS가 적용된 Supabase에 저장된다.
- 앱이 Netlify에 배포된다.
- 첫 이벤트 리허설이 데스크톱과 모바일에서 통과한다.

NStack 파일럿은 다음 조건을 만족하면 성공으로 본다.

- 각 Phase마다 작업 지시서와 완료 보고서가 남아 있다.
- 주요 의사결정과 구현 지식이 LLMWiki에 기록되어 있다.
- Supabase, Netlify, GitHub, SwarmVault 연결 절차가 재현 가능하게 정리되어 있다.
- NStack 스킬과 규칙의 개선점이 구체적으로 도출되어 있다.
- Moras 경험을 다음 프로젝트의 표준 절차로 재사용할 수 있다.
